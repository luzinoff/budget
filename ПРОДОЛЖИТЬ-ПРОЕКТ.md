# Приложение учёта бюджета — передача проекта

Это описание текущего состояния проекта: что уже сделано, как устроено, как развернуть с нуля и что нельзя ломать при доработке.

Чтобы продолжить работу с Клодом на другом компьютере, откройте разговор со словами «продолжаем проект учёта бюджета» и дайте доступ к папке с этими файлами. Всё нужное изложено ниже.

## Состав папки

| Файл | Назначение |
|---|---|
| `index.html` | Всё приложение целиком: разметка, стили, логика. Единственный файл, который правится. |
| `sw.js` | Service worker — офлайн-режим и кэш |

| `Бюджет-копия-ГГГГ-ММ-ДД.json` | Резервная копия данных, выгруженная из приложения |
| `ПРОДОЛЖИТЬ-ПРОЕКТ.md` | Этот файл |

## Что это

Личный учёт доходов и расходов для человека, живущего во Вьетнаме: часть денег в рублях, часть во вьетнамских донгах. Начиналось как таблица в Excel, затем стало одностраничным приложением, а сейчас — PWA, размещённая на GitHub Pages и синхронизируемая через Google Диск.

Чистый JavaScript, без фреймворков, без сборки, без пакетов. Правится текстовым редактором, выкладывается копированием файлов. Единственная внешняя зависимость — скрипт входа Google, и тот подгружается только когда пользователь сам нажал синхронизацию.

Данные хранятся в `localStorage` браузера под ключом `budget.v1`, а их копия — в скрытой служебной папке Google Диска.

## Требования пользователя — их нельзя нарушать при доработке

Донги **не пересчитываются** в рубли. Это принципиально: две валюты живут раздельно, курс не нужен.

Комментарий и способ оплаты относятся **к каждой отдельной записи**, а не к категории. Поэтому данные хранятся журналом транзакций, а не таблицей «день × категория» — в ячейку таблицы это не помещается.

Ввод даты, категории и способа оплаты — **только выбором**, кнопками-чипами. Руками вводятся лишь сумма и комментарий; ещё есть диктовка голосом.

## Что умеет

Вкладки слева направо: Траты ₫, Кошельки (карта BIDV и наличные), Доходы, Траты ₽, Итоги, Динамика. Открывается приложение на «Расходы ₫» — это самая частая операция. Вкладки — нижнее меню с иконками (под большой палец), сверху только месяц и точка синхронизации. У каждого раздела свой цвет — `--acc` в CSS, его ставит `setTab()` через `body[data-tab]`: донги оливковые, наличные янтарные, рубли синие; им окрашены кнопка «Добавить», выбранные чипы, итоги и пункт меню. Чип дня показывает число и день недели (выходные — красным). Строка ввода — сетка `.entry`: микрофон, сумма, «Добавить», под ними комментарий; на широком экране всё в одну строку. Сверху переключатель месяца и года; если выбранный год выходит за диапазон списка, недостающий год подставляется сам.

Донговые расходы группируются по дням с подытогом на каждый день. Есть итог месяца, разбивка по категориям и по способам оплаты с процентами, и среднее по дням, в которые были траты.

Наличные: вводится остаток на начало месяца, отмечаются пополнения, и на каждый день считается остаток с учётом трат наличными за этот день. Дни без движения не показываются.

Способы оплаты донговых трат (`CATS.pay`): Наличные, Карта BIDV, Карта UnionPay, Карта ППМ, Карта Bybit, Русский QR. Кошельками на «Кошельках» считаются только BIDV и наличные; ППМ и Bybit, как и UnionPay, просто способы оплаты. Голосом: «ппм», «пэ пэ эм», «байбит», «bybit» (`V_PAY`). В `vRest()` ключи вырезаются от длинных к коротким, иначе от «картой ппм» в комментарии оставалось «картой».

Диктовка: кнопка микрофона в каждой форме использует Web Speech API. Разбирает суммы цифрами и словами, множители «тыщ», «лям», «млн», категории и способы оплаты по ключевым словам, а текст в кавычках кладёт в комментарий. Дату понимает как «сегодня», «вчера», «позавчера» или цифрой — «15 числа», «15го»; словесные порядковые вроде «пятнадцатого» не распознаются. Если названная дата попадает в другой месяц, приложение переключит месяц целиком. Работает в Chrome; в браузерах без поддержки кнопка просто отключена.

Синхронизация с Google Диском работает сама: после первого входа приложение обменивается данными при запуске, после каждой правки, при возврате к вкладке и при закрытии — без единого нажатия. Точка в шапке показывает состояние, и в неё же выносится просьба войти заново, если разрешение протухло.

Импорт BIDV: на вкладке «Расходы ₫» кнопка «Импорт BIDV» читает папку `transactions` репозитория `luzinoff/BIDV` через GitHub API (без входа, поэтому репозиторий должен быть публичным). Каждый `.json` там — одна операция с полями `reference_number`, `transaction_at`, `amount_vnd`, `recipient_name`. Новые файлы показываются в окне: для каждой отмеченной операции выбирается категория или «⊘ Удалить» (не добавлять, но больше не показывать). Слева от мерчанта — поле для своего комментария; в запись идёт «комментарий мерчант» через пробел (пустые части пропускаются), мерчант тоже можно поправить. Сумма делится на 1000 — донги учитываются в тысячах. Способ оплаты — «Карта BIDV». Время `transaction_at` приходит без часового пояса и считается временем Вьетнама (UTC+7) независимо от пояса устройства — это делает `parseBidvDateTime()`. Оплата картой в валюте (`transaction_type: "card_payment_foreign"`, `amount_vnd: 0`, `original_amount`, `original_currency`) приходит без суммы в донгах: банк спишет её через 1–2 дня двумя строками выписки (сумма и комиссия, комиссия бывает 3–4%), в описании строки есть код операции (`reference_number`, он же Approval code). В окне импорта у такой операции вместо суммы поле ввода с подсказкой «22,22 USD · код 905440»; вписывают итог в тысячах или как в выписке, можно через плюс — `bidvFxAmount()`: слагаемые от 100 000 считаются полными донгами и делятся на 1000. Пока поле пустое, операцию не добавить (можно «⊘ Удалить»). Комментарий по умолчанию — сумма в валюте.

Импорт Bybit: кнопка «Импорт Bybit» стоит в карточках «Новый расход, ₽» и «Внесение» (на «Кошельках»), обе вызывают `p2pImport()` (префикс `p2p`, потому что `bybitImport`/`bybitBusy` уже заняты загрузкой остатков на «Капитале»). Читается папка `bybit` того же репозитория `luzinoff/BIDV`; файлы `bybit-<время>-<цифры ID>.json` с полями `side` (buy/sell), `fiat_amount`, `fiat_currency`, `crypto_amount`, `crypto`, `created_at` (UTC, с Z), `order_tail` кладёт тот же сборщик из выполненных P2P-ордеров. Покупка за RUB → запись в «Траты ₽» с категорией «Покупка иностранной валюты», сумма в рублях; продажа за VND → внесение (`topup`) на карту BIDV, сумма делится на 1000, `cat` пустой («Обмен, перевод»). Другие пары валют пропускаются. Дата — по времени Вьетнама через `parseBidvDateTime()`, `opTs` — время ордера. Комментарий по умолчанию «Bybit P2P 411,16 USDT», его можно править. Если в тот же день уже есть запись с той же суммой (рубли — точно, донги — ±1 тыс.), ордер помечается «уже есть?» и для него заранее выбрано «⊘ Удалить». Обработанные файлы пишутся в те же метки `DB._meta.bidvImported`: имена `bybit-…` с `bidv-…` не пересекаются, так что слияние и синхронизация меток общие.

Вкладка «Динамика» (последняя, после «Итогов») — сравнение месяцев, только чтение базы. Период — 6 или 12 месяцев либо всё время, кончается месяцем в шапке; пустое начало окна обрезается (`dynMonths()`, минимум 3 месяца), выбор хранится в `localStorage["budget.dyn.n"]`. Рубли: парные столбцы доходов и расходов (цвета `#22985E` / `#2D62B8` проверены на различимость, в т. ч. при дальтонизме) и таблица с разницей. Донги: столбцы расходов, среднее по завершённым месяцам, у текущего месяца пунктиром — прогноз по темпу трат. Ниже две тепловые таблицы «категория × месяц», оттенок нормирован по строке. Графики — inline SVG без библиотек; ширина берётся из карточки, поэтому `renderDyn()` рисует только видимую вкладку (зовётся из `render()`, `setTab("dyn")` и по `resize`). Подсказка — `.dyn-tip`: наведение на ПК, касание на телефоне. Класс строки «Всего» в таблицах — `t-sum`: `.tot` уже занят строками итогов (`display:flex`) и ломал таблицу. Подписи нижнего меню укорочены, чтобы шесть вкладок влезли в телефон: «Траты ₫», «Наличка», «Доходы», «Траты ₽», «Итоги», «Динамика».

Разбор месяца от ИИ: карточка на «Итогах» перед Google Диском. Gemini получает выбранный месяц (рубли — итоги, категории, все записи; донги — категории, способы оплаты, траты по дням, все записи с комментариями; наличные) и итоги двух предыдущих месяцев для сравнения, а отвечает по формату «Коротко / Куда ушли деньги / По сравнению с прошлыми / На что обратить внимание / Советы». Сделано по образцу советов Gemini в Дневнике (папку Дневника только читали). Ключ — `localStorage["budget.ai.key"]`, модель — `budget.ai.model` (по умолчанию `gemini-3.6-flash`); в базу, на Диск и в копии они не попадают, на каждом устройстве ключ вводится отдельно (кнопка-шестерёнка в карточке). Что уходит наружу — только то, что собирает `aiPrompt()`: это белый список, новое поле записи само не уйдёт. Кнопка «Что отправится» показывает ровно этот текст. Ответ рисуется `aiRender()` через `textContent` (жирный, заголовки, пункты), чужой HTML не исполняется. Запрос — `aiCall()`, лимит 16384 токенов и таймаут 180 с, как в Дневнике: у Gemini 3 размышления входят в лимит; части с `thought` отбрасываются. Ошибка держится в карточке (`AI.err`) до следующей попытки, состояние запроса (`AI.busy`) — по ключу месяца, переключать вкладки и месяцы можно.

«Капитал» — отдельный экран, открывается иконкой-стопкой монет в шапке (в нижнее меню не входит: шесть вкладок уже на пределе). Повторное нажатие возвращает на прежнюю вкладку (`lastTab`); на этом экране переключатель месяца скрыт — капитал от месяца не зависит. Цвет раздела — `--cap` (бирюзовый). Состав: сводка (чистый капитал = активы − ипотека, разбивка «вклады и счета / стейблкоины / рискованные», подушка в месяцах трат, отложено, норма сбережений), «Вклады и счета», «Крипта · Bybit», «Ипотека», «Финансовые цели», «Риск-профиль» (тест из 6 вопросов → консервативный / умеренный / агрессивный, ориентир доли рискованных активов и советы по правилам из `capTips()`). Средние траты и доход — медиана трёх последних полных месяцев по рублям, без «В накопления»; донги не участвуют и в рубли не пересчитываются (их стоимость уже видна в «Покупке иностранной валюты»). Курс доллара и цены монет — по кнопке «Обновить курсы»: ЦБ (cbr-xml-daily.ru), Bybit public API, запасной вариант CoinGecko; наружу уходят только тикеры. Можно задать вручную, нажав на строку курса. Стейблкоины без цены считаются по 1 $.

На «Капитале» ИИ — одна карточка «Спросить ИИ» (как в Медкарте): готовые вопросы на виду (`CHAT_PRESETS_CAP`, первый — полный разбор капитала), поле своего вопроса, выбор данных и периода, прошлые разговоры. Это та же переписка, что и окно «Задать вопрос» с «Итогов» (`chatView(box, o)` — общий вид; у каждого места свой открытый разговор, ожидание ответа общее, `CHAT.views`). Пока в поле печатают, обычная перерисовка его не трогает. Отдельного «Разбора капитала» больше нет: старый сохранённый разбор (`DB._meta.ai.cap`) один раз переносится в разговоры (`capAiMigrate()`, id из времени разбора, чтобы перенос на двух устройствах не задвоился), а `ai.cap` помечается удалённым. Выжимка капитала для вопросов — `capAiPrompt()`, стоимость активов — `capSummary()`.

Загрузка остатков Bybit — кнопка «Загрузить с Bybit» в карточке крипты, ключ — шестерёнка там же. Запросы идут прямо из браузера к `api.bybit.com` (v5), подпись HMAC-SHA256 через Web Crypto (`bybitGet()`), перед ними берётся время сервера (`bybitOff`), окно подписи 20 с. Читаются три счёта: Trading (`/v5/account/wallet-balance`, UNIFIED с запасным SPOT), Funding (`/v5/asset/transfer/query-account-coins-balance?accountType=FUND`), Earn (`/v5/earn/position?category=FlexibleSaving`); счёт, который не прочитался, не трогается. Монеты с биржи — записи crypto с `src:"bybit"` и `acct`; при загрузке количество перезаписывается, пропавшие удаляются, ручные записи не трогаются (при первой загрузке предлагается убрать ручные записи со словом Bybit). Время загрузки — `cap.rates.byTs`. Ключ и секрет — `localStorage["budget.bybit.key"/"budget.bybit.secret"]`, в базу, на Диск, в копии и в разбор ИИ не попадают. Нужен ключ только на чтение без привязки к IP. Если Bybit не пустит запрос с ключом из браузера (CORS), приложение так и пишет — тогда нужен свой прокси на сервере вне США (VPS пользователя стоит в США, Bybit его блокирует).

Вопросы к ИИ — переписка с Gemini, как «Спросить ИИ» в Медкарте. Открывается кнопкой «Задать вопрос» в карточке разбора месяца («Итоги») и в карточке разбора капитала; окно `chatOpen()`. Перед первым вопросом выбираются разделы (Рубли, Донги, Записи с комментариями, Капитал) и период (3 мес., полгода, год, всё время) — выбор запоминается в `localStorage["budget.chat.opt"]` и сохраняется в разговоре. Выжимка `chatContext()` (белый список) собирается заново при каждом вопросе и уходит первым сообщением, дальше — вся переписка (`aiCall()` принимает массив `contents`). Инструкция — `CHAT_SYS`. Разговоры — `DB._meta.chats` (`chatsNorm()`/`chatsMerge()`: слияние по id, побеждает больший `at`, удаление — надгробие на 90 дней, не больше 100 разговоров и 60 сообщений в каждом), синхронизируются через Диск. Вопрос без ответа (ошибка Gemini) не сохраняется и возвращается в поле ввода. Окно можно закрыть во время ожидания — ответ допишется сам.

Вкладка «Кошельки» (бывшая «Наличка», внутренний ключ вкладки по-прежнему `cash`): сверху карта BIDV, под ней наличные — у каждого остаток на сегодня (или на конец месяца) и поле «Было на начало месяца» (`bidvStart`/`bidvStartTs` и `cashStart`/`cashStartTs`, сливаются по метке времени одинаково). Внесения — список `topup`: `pay: "Карта BIDV"` — на карту, иначе (в том числе пустой у старых записей) — наличные; наличные с `cat: "С карты BIDV"` — снятие с карты (плюс наличным, минус карте). Траты списываются по способу оплаты из «Трат ₫», включая импорт BIDV. Расчёт — `walletRows(k, m, n)`, кошельки описаны в `WALLETS`. «Остаток по дням» переключается чипами между кошельками. Карта BIDV добавлена в «Итоги», CSV, разбор месяца и выжимку для вопросов к ИИ. Голосом: «на карту», «наличные», «снял» выбирают кошелёк и источник.

Памятка на «Капитале» — карточка перед «Спросить ИИ», кнопка «Изменить». Текст с разметкой (### заголовок, «- » пункт, **жирный**) и дата «за границей с»; по дате считается налоговое резидентство (`capResidency()`: дни за границей, статус по последним 12 месяцам и итог за календарный год, без учёта поездок обратно). Хранится в `DB._meta.cap.notes {text, abroad, ts}`, сливается по `ts`. Пока памятку не правили, показывается общий текст `CAP_MEMO_DEFAULT` (налоги нерезидента, что это значит для накоплений, за чем следить) — в коде нет личных данных, потому что репозиторий публичный; дата отъезда вводится в приложении. Памятка и статус резидентства уходят в выжимку для вопросов к ИИ (`capAiPrompt()`).

Категория «В накопления» во «Тратах ₽» входит в расходы, но выделена бирюзовым: полоса у записи, строка «в т.ч. в накопления» под итогом и на «Итогах». При её выборе появляется ряд «Куда отложили» — id актива пишется в поле `pay` рублёвой записи, в списке показывается «→ название». Рублёвый вклад или счёт показывает сумму, введённую вручную на дату `amountTs`, плюс такие пополнения, добавленные позже; у крипты — «вложено из бюджета». Ипотека считается по графику банка (`capMortSim()`): остаток основного долга на дату `asOf`, ставка, аннуитетный платёж, день платежа `payDay`, дата окончания договора `end`. Проценты начисляются по дням (ставка/365, в високосный год /366) от платежа до платежа, последний платёж — в день окончания договора; с графиком Сбера совпадает до копеек (проверено на реальном графике: 207 платежей, переплата 975 240 ₽). Остаток уменьшается сам при наступлении платёжных дат, записи «ипотека» в бюджете на него не влияют. Досрочное погашение — запись во «Тратах ₽» со словом «досрочн» в комментарии, добавленная после ввода остатка: вся сумма идёт в основной долг.

На вкладке «Итоги» — настройки синхронизации и работа с файлами: выгрузка копии в JSON, загрузка обратно в двух режимах (объединить или заменить) и выгрузка в CSV для Excel с BOM, разделителем `;` и запятой в дробной части, чтобы русский Excel открыл корректно.

## Донги: хранятся полностью, показываются в k (15 ноября 2026)

С версии кэша `budget-v43` донги хранятся полными суммами (45 000), а не в тысячах (45), как было раньше. Показ — `fV()`/`fK()`: «45k», «45,5k», от миллиона — целые k («1 500k»). Ввод по-прежнему в тысячах: в формах, окне карандаша и полях «Было на начало месяца» «45» означает 45 000 ₫, «45k» тоже понимается (`vIn()`; обратно в поле — `vOut()`). Голосом «45» — тысячи, «45 тысяч» / «1,5 млн» — полная сумма (`amountFull` в `vParse()`). Импорт BIDV и продажи Bybit пишут полные донги (без деления на 1000), валютная оплата из выписки (`bidvFxAmount()`) тоже возвращает полные донги. Для ИИ донги по-прежнему подаются в тысячах (`aiV()` делит на 1000), подписи «тыс. ₫» в инструкциях верны. CSV теперь в полных донгах.

Переход без смешения единиц: новые ключ `localStorage["budget.v2"]` и файл на Диске `budget.v2.json`. При первом запуске новой версии `load()` берёт `budget.v1` и переводит его функцией `dbFromV1()` (×1000 у `vnd`, `topup`, `cashStart`, `bidvStart`; рубли и `_meta` не трогаются); старый ключ остаётся как есть. При обмене `syncNow()` читает `budget.v2.json` и, если старый `budget.v1.json` менялся после последнего переноса (`modifiedTime` новее `DB._meta.v1`), переводит и вливает и его — так подхватываются записи с устройства, где ещё открыта старая версия. В `budget.v1.json` новая версия не пишет никогда. Метка `_meta.v1` хранится в базе и синхронизируется, чтобы новое устройство не тянуло старый файл заново и не воскрешало давно удалённое. Копия JSON теперь помечена `_v: 2`; копия без пометки при загрузке считается старой и пересчитывается ×1000.

Всё, что ниже в этой записке говорит «в тысячах» или «делится на 1000» про хранение донгов, относится к версиям до `budget-v43`.

## Развёртывание

### 1. GitHub Pages

Все файлы кладутся в корень репозитория. В настройках репозитория раздел Pages, источник — ветка `main`, папка `/ (root)`. Через минуту сайт доступен по адресу `https://ИМЯ.github.io/РЕПОЗИТОРИЙ/`.

Репозиторий может быть публичным — в коде нет секретов. Client ID секретом не является, он по замыслу виден в браузере; доступ ограничивается списком разрешённых адресов в консоли Google, а не скрытностью идентификатора.

HTTPS обязателен. Проверка одна на всё — `const httpsOk = location.protocol === "https:"`, и ею закрыты и вход в Google, и регистрация service worker. Практическое следствие: при открытии файла двойным кликом синхронизации и офлайна не будет, о чём приложение честно пишет в интерфейсе. Но и на `http://localhost` тоже — хотя браузер там service worker разрешает, этот код его не включит. Значит офлайн-режим проверяется только на выложенном сайте; для локальной разработки это нормально, вёрстка и вся логика ввода работают и с файла.

В [Google Cloud Console](https://console.cloud.google.com/) создайте проект. Включите **Google Drive API**. Приложение можно навсегда оставить в статусе тестового — проверка Google для личного использования не нужна, надо лишь раз в полгода подтверждать доступ заново.

Область доступа — только `drive.appdata`. Это самый узкий скоуп из существующих: приложение видит исключительно свой файл в скрытой папке и не имеет доступа к остальному Диску. Обычно он не требует верификации.

Полученный Client ID вставьте в приложении на вкладке «Итоги» в поле Client ID и нажмите «Сохранить». Он останется в этом браузере; на втором устройстве вводится тот же самый.

## Модель данных

```js
DB["ГГГГ-ММ"] = {
  inc:   [],   // доходы, ₽
  rub:   [],   // расходы, ₽
  vnd:   [],   // расходы, ₫
  topup: [],   // пополнения налички, ₫
  cashStart: 0,      // остаток налички на начало месяца, ₫
  cashStartTs: 1     // когда остаток менялся — для слияния
}
```

Запись: `{ id, day, amount, note, cat, pay, ts, opTs, del }`.

`opTs` — фактическое время операции (мс), есть у импортированных из BIDV; по нему записи сортируются внутри дня. У ручных записей 0, тогда используется `ts`.

Кроме месяцев в базе есть служебный ключ `DB._meta = { bidvImported: [{ref, ts}], ai: {"ГГГГ-ММ": {text, at, model, cut?}}, cap: {items, rates, profile} }`. `cap.items` — вклады, счета, монеты, ипотека и цели `{id, kind, ts, del, …}`, сливаются по `id` как операции (надгробие `{id, kind, ts, del}` на 90 дней); `cap.rates` — `{usd, usdTs, px, pxTs}`, побеждает более свежая метка; `cap.profile` — ответы теста `{a, ts}`. Нормализация — `capNorm()`, слияние — `capMerge()`, писать только через `capSave()`. Разборы ИИ сливаются по `at` (побеждает более поздний), удаление — надгробие `{at, del:1}` на 90 дней, иначе разбор вернулся бы с другого устройства. Всё содержимое `_meta` нормализует `metaNorm()` — её используют `prune()`, `mergeDB()`, загрузка копии и `bidvSaveImported()`; писать `DB._meta = {…}` в обход неё нельзя, потеряется соседнее поле.

Про метки BIDV: `DB._meta.bidvImported` — имена уже обработанных файлов BIDV. Синхронизируется вместе с базой, сливается по `ref`, срока жизни у меток нет (иначе старые файлы из репозитория снова всплыли бы в окне импорта). Через `fix()` его не пропускать — это не месяц.

`id` уникален и неизменен, `ts` — момент последней правки, `del` — момент удаления (0 у живой записи). Поле `pay` заполняется только у донговых расходов.

**Удаление не стирает запись, а помечает её.** Иначе стёртое на одном устройстве воскресало бы с Диска на другом. Такие «надгробия» живут 90 дней (`TOMB_TTL`), после чего вычищаются в `prune()`. Наружу, в интерфейс, отдаются только живые записи — за это отвечает `mon()`, тогда как `monW()` даёт полный доступ для записи.

## Синхронизация

Вход через Google Identity Services, обращения к Drive API напрямую через `fetch`. Один файл `budget.v1.json` в папке `appDataFolder`.

Порядок работы `syncNow()`: получить токен, найти файл на Диске, скачать, слить с локальной базой, сохранить результат и локально, и на Диск.

`mergeDB()` объединяет две базы по `id` записи: побеждает бо́льший `ts`, а при равенстве — удаление. Остаток налички сливается отдельно по `cashStartTs`. Благодаря этому порядок работы устройств не имеет значения и офлайн безопасен.

Автосинхронизация запускается через 2 секунды после правки. Живого токена для этого не требуется: достаточно, чтобы вход когда-то был сделан — этот факт хранится в `localStorage["budget.auth"]` (в памяти — `SYNC.ever`), потому что сам токен живёт только в памяти вкладки и теряется при перезагрузке. Благодаря флагу приложение продлевает токен молча, с `prompt:"none"`, и обменивается данными само: при запуске, после каждой правки, при возврате к вкладке и при закрытии страницы. Флаг `SYNC.pending` следит, чтобы правка, сделанная во время выгрузки, не потерялась, а `flushSync()` дожимает отложенную правку на `pagehide`.

Тихое продление может не пройти — Google разлогинен, почищены куки, Safari или Firefox режут сторонние куки. Тогда взводится `SYNC.relogin`: автосинхронизация замолкает до нажатия кнопки, а на «Итогах» появляется просьба войти заново. **Окно входа Google в фоне не открывается никогда** — только по нажатию «Войти и синхронизировать». Это главное правило этого блока: всплывающее окно, выскочившее само по себе, пользователь воспринимает как поломку. За разделение отвечает закрытый список `AUTH_MSGS`; ошибки Диска и таймауты сети в него не входят, они лечатся повтором.

Сорванный обмен повторяется сам с нарастающей паузой (`SYNC.fails`, от 5 секунд до минуты, таймер `SYNC.retry`). Повтор намеренно держится отдельно от таймера автоотправки `SYNC.timer`: иначе `flushSync()` принял бы его за отложенную правку и обнулял выдержку на каждое сворачивание приложения.

Возврат к вкладке синхронизирует не чаще раза в 30 секунд — на телефоне переключение между приложениями иначе гоняло бы полный цикл записи на Диск.

Отключение синхронизации во время летящего запроса обработано через счётчик поколений `SYNC.gen`: `authOff()` увеличивает его, а начатый обмен сверяет своё поколение на каждом шаге и тихо сходит с дистанции. Без этого прилетевший позже ответ Google снова записал бы флаг входа, и отключение отменялось бы само собой. По той же причине `authOff()` гасит таймеры и снимает `SYNC.busy`, а событие `storage` разносит отключение по остальным открытым вкладкам.

Отдельно обработан редкий случай: если два устройства синхронизировались впервые одновременно, на Диске может появиться два файла. Тогда берётся старейший как основной, остальные сливаются в него и удаляются — но только после успешной записи.

Кнопка синхронизации в шапке (`#hsync`, как в Медкарте): значок обновления, точка состояния и короткий статус — время последнего обмена, «Обмен…», «Ошибка», «Войти», «Не настроено», «Локально»; полная причина — в подсказке. Нажатие сразу запускает `syncNow(true)` — это действие пользователя, поэтому окно входа Google здесь допустимо. Без Client ID кнопка ведёт на «Итоги» к настройке, на `file://` только объясняет, что синхронизация работает лишь на сайте. Статус обновляет `hsyncUI()`, её зовёт `syncUI()`. На телефоне виден только значок с точкой в углу, а при ширине до 420px из шапки убрано название «Бюджет» — иначе оно обрезалось до «Бю…».

Точка на вкладке «Итоги» показывает состояние: серая — выключено, зелёная — подключено, красная — ошибка. Фоновые сбои тоже красят её и пишут причину: молчать об этом нельзя, иначе пользователь решит, что данные в безопасности.

## Уже исправленные проблемы — не сломать повторно

Импорт JSON проверяет данные через `isObj()`. Поскольку `typeof null === "object"`, файл с `null` раньше затирал всю базу без возможности восстановления. Каждая запись при загрузке нормализуется в `fix()`, а ключи месяцев проверяются регулярным выражением.

Режим «Заменить из копии» не выбрасывает записи молча, а помечает удалёнными с текущей меткой времени. Иначе синхронизация вернула бы их с Диска и замена оказалась бы мнимой.

Поле остатка налички не перерисовывается, пока в нём стоит курсор, иначе ввод стирался на каждом нажатии. Сохранение отложено на 400 мс, потому что `save()` прогоняет `prune()` по всей базе. И `cashStartTs` не обновляется, если значение не изменилось: иначе простой заход в поле создал бы свежую метку с нулём и затёр остаток с другого устройства.

Суммы вводятся в поля `type="text" inputmode="decimal"` и разбираются функцией `parseAmt()`, которая понимает запятую, точку и пробелы-разделители тысяч. С `type="number"` браузер возвращал пустую строку на «1,5».

В CSV текст, начинающийся с `=`, `+`, `-`, `@`, экранируется апострофом — иначе Excel исполнит его как формулу.

Все данные пользователя выводятся через `textContent`, не через `innerHTML`.

Карандаш ✎ у записи (донги, рубли, доходы, внесения) открывает окно `editRecord(key, id)`: день (список с днём недели), категория и способ оплаты чипами, «Куда отложили» у «В накопления», сумма и комментарий. Месяц записи запоминается при открытии, сохранение — в `DB[k]` с новым `ts`; без изменений запись не трогается. На ПК курсор сразу в сумме, на телефоне клавиатура не открывается, чтобы не закрыть чипы. Прежний выпадающий список категории в строке убран.

У внесения (`key "cash"`, список `topup`) в окне вместо категории — «Куда» (карта BIDV / наличные) и для наличных «Откуда» (обмен или «Снял с карты BIDV» — пометка `cat = FROM_BIDV`). Если кошелёк не меняли, `pay` записи не трогается (у старых внесений он пуст и означает наличные); прочие пометки в `cat` сохраняются.

Обмен между кошельками (карта BIDV ↔ наличные): в карточке «Внесение или обмен» переключатель «Операция» — «Внесение» (деньги пришли извне, выбирается «Куда») или «Обмен карта ↔ наличные» (выбирается «Направление»). Хранится как запись в `topup`: карта → наличные — `pay "Наличные"`, `cat FROM_BIDV` («С карты BIDV», так же хранились прежние «снятия» — они автоматически стали обменами); наличные → карта — `pay BIDV_PAY`, `cat FROM_CASH` («С наличных»). Признак — `isXfer(x)`. В `walletRows()` у кошелька-получателя это приход, у источника — списание; в доходы, расходы, «Всего за месяц» внесений, сумму дня в списке и «внесено» в данных для ИИ обмен не входит (для ИИ — отдельной строкой «обмен пришло/ушло»). В окне правки внесения тот же переключатель. Голосом: «снял», «банкомат» — карта → наличные; «положил/внёс … наличные на карту» — наличные → карта.

Купил крипту за рубли и часть оставил: оставленное — сбережение, а не трата. В окне импорта Bybit у каждой покупки за рубли есть поле «Оставил, USDT» и выбор монеты в «Капитале» (по умолчанию та же монета, сначала счёт Funding — `p2pKeepOpts()`). Если поле заполнено, покупка делится по цене ордера (`p2pSplit()`): «Покупка иностранной валюты» на остаток и «В накопления» с `pay` = id актива на оставленную часть; если оставлено всё — запись целиком становится «В накопления». Для уже внесённых покупок то же делает кнопка «Разделить: часть оставил в накоплениях» в окне карандаша у записи «Покупка иностранной валюты»: если в комментарии есть «N USDT» (`p2pNoteCoins()`), вводятся монеты, иначе рубли. После разделения в комментарии покупки число монет заменяется на оставшееся (`p2pNoteSetCoins()`), чтобы повторное разделение считало долю верно. Так рублёвые траты и средние траты «Капитала» не включают отложенное, а у монеты видно «вложено из бюджета». Привязка — по id актива: если при загрузке с Bybit монета пропадёт со счёта (например, переведена Funding → Trading), запись покажет «актив удалён», и её можно перепривязать карандашом.

Пара «покупка за рубли — продажа части за донги» в один день считается сама (`p2pAutoKeep()`): по каждому дню (по времени Вьетнама) и монете оставлено = куплено − продано; если плюс — делится между покупками дня пропорционально купленному и подставляется в «Оставил» (`o.autoKeep`), рядом подпись «в тот же день куплено N, продано M». Если продано не меньше купленного или продажи в тот день нет — поле пустое. Число можно поправить. В окне карандаша «Разделить» то же: продажи этой монеты в тот же день ищутся среди внесений с «Bybit» в комментарии, остаток подставляется.

Удаление записи (×) спрашивает подтверждение своим окном `askConfirm()`, а не `confirm()`: в окне видно, что удаляется (категория, сумма, дата, оплата, комментарий). Фокус стоит на «Отмена», чтобы случайный Enter ничего не стёр; Esc и нажатие мимо окна — тоже отмена. Месяц записи запоминается до вопроса, удаление идёт по `DB[k]`, а не через `monW()`.

`buildForm(key, scroll)` принимает второй аргумент, поэтому её нельзя передавать напрямую в `forEach` — индекс массива попадёт в `scroll` и страница будет прыгать.

`setTab()` вызывается после `render()`, иначе лента дней пересобирается и прокрутка сбрасывается.

В `parseBidvDateTime()` регулярное выражение должно быть с одиночными `\d`. Двойные `\\d` в литерале регулярки не совпадают ни с чем, и строка уходила в `new Date()`, который читал её в поясе устройства: на компьютере с московским временем вечерние операции попадали на следующий день.

Миграция `ts` из секунд в миллисекунды срабатывает только на правдоподобных секундах (`1e9…1e12`). С условием «`< 1e12`» записи с `ts: 1` умножались на 1000 при каждом `fix()` и получали мусорный `opTs`; такие `opTs < 1e11` теперь обнуляются.

Окно BIDV сначала проверяет все отмеченные строки и лишь потом пишет в базу — иначе после «выберите категорию» и повторного нажатия часть операций добавлялась дважды. Поиск элементов — только внутри своего окна (`overlay.querySelector`).

Загрузка JSON-копии сохраняет `_meta`; режим «Заменить» его не трогает.

`today` — не константа: `refreshToday()` при возврате к приложению замечает смену даты, переставляет выбранный день и, если смотрели текущий месяц, переходит в новый. Иначе PWA, сутками висящая в памяти телефона, предлагала вчерашний день.

Service worker не трогает запросы к чужим доменам: закэшированный ответ Google сломал бы вход.

## Проверка

Сборки и тестов в проекте нет. Синтаксис скрипта проверяется `node --check` по вырезанному из `index.html` блоку `<script>`, поведение — в headless-Chromium (Playwright) с подгруженной в `localStorage` резервной копией, в том числе с разными часовыми поясами. Вход Google и офлайн проверяются только на выложенном сайте.

## Возможные доработки

Иконки сейчас только в SVG. Chrome на Android их понимает, но некоторые лаунчеры и iOS — нет, поэтому PNG 192×192 и 512×512 не помешают.

Упаковка в настоящий APK через Capacitor, если PWA окажется недостаточно. Практической разницы почти нет: PWA уже даёт иконку, офлайн и полноэкранный запуск.

Репозиторий с выписками BIDV публичный (иначе API без токена его не отдаст) — значит, суммы, получатели и время операций видны любому. Если это нежелательно, нужен приватный репозиторий и токен с правом только на чтение, вводимый на «Итогах» как Client ID.

GitHub API отдаёт из одной папки не больше 1000 файлов. Когда в `transactions` их станет больше, старые обработанные файлы стоит переносить в архивную папку.

Диктовка опирается на Web Speech API, который в Chrome отправляет звук на серверы Google. Офлайн она не работает.

## Переезд на другой компьютер

Исходники самодостаточны: скопируйте папку целиком, и разработку можно продолжать. Ничего не собирается и не устанавливается.

Но три вещи живут вне папки и переносом файлов не подхватываются.

**Данные.** Они в `localStorage` браузера, а не в файлах. Перед переездом откройте «Итоги» → «Сохранить копию» и возьмите свежий JSON с собой; на новом месте — «Объединить с копией». Лежащая в папке копия датирована днём выгрузки и с тех пор устарела. Если синхронизация с Диском уже настроена, проще войти в неё на новом устройстве — данные приедут сами.

**Client ID.** Хранится в `localStorage["budget.cid"]`, в файлах его нет. Вводится заново на вкладке «Итоги» — возьмите из раздела «Координаты проекта» выше или из Google Cloud Console.

**Настройки Google Cloud.** Сам проект, включённый Drive API, список тестовых пользователей и разрешённые origins остаются в консоли и никуда не деваются. Трогать их нужно, только если поменяется адрес сайта: тогда новый origin надо дописать, иначе вход перестанет работать.

Установленная на телефоне PWA, кэш service worker и метка последней синхронизации восстанавливаются сами.

## Общие настройки с дневником и медкартой (14.11.2026)

Бюджет, дневник и медкарта открываются с одного сайта `luzinoff.github.io`
и видят одну память браузера. Client ID Google и ключ с моделью Gemini
лежат ещё и в общей записи `luz.shared.v1`: ввёл или поменял в любом из
трёх приложений — остальные подхватили, даже открытые в соседней вкладке
(событие `storage`). Блок `luzShared` одинаковый во всех трёх файлах;
у каждого приложения свой переходник к своим настройкам (здесь —
`luzBudgetOwn()`/`luzBudgetApply()` над `budget.cid`, `budget.ai.key`,
`budget.ai.model`). При запуске общее побеждает; поля, которых в общем
ещё нет, заполняются своими. В общее при сохранении уходит только то, что поменяли
в этой вкладке, — иначе вкладка со старыми значениями затёрла бы свежие.
Удаление ключа тоже общее.

Выбор ИИ: Gemini или DeepSeek (18.11.2026). В общую запись `luz.shared.v1` добавлены поля `aiProvider` ("" — Gemini, "deepseek" — DeepSeek), `dsKey`, `dsModel` (пустая модель — `deepseek-flash`). Переключатель общий для дневника, бюджета и медкарты: поменяли в одном — подхватили остальные. Блок `luzAi()` / `luzAiErr()` одинаковый во всех трёх файлах (стоит сразу после `luzShared`): принимает переписку в формате Gemini (`role user/model`, `parts[{text}]`) и для DeepSeek переводит её в OpenAI-формат (`https://api.deepseek.com/chat/completions`, `Authorization: Bearer`), ответ — `{text, model, cut, provider}`, коды ошибок прежние (NO_KEY, TIMEOUT, NETWORK, EMPTY) плюс NO_FILES. Ход размышлений DeepSeek (`reasoning_content`) не берётся. Распознавание PDF и фото в медкарте (`handleAIFiles` → `gemini(parts)` с `inline_data`) всегда идёт через Gemini, независимо от переключателя. DeepSeek хранит запросы в Китае и по умолчанию может учиться на них — об этом пишет окно настроек. Запрос к DeepSeek прямо из браузера (CORS) заранее не проверен: если не пустит, ошибка подскажет вернуться на Gemini. Здесь: ключи `localStorage["budget.ai.provider" / "budget.ds.key" / "budget.ds.model"]`, переключатель — чипы в окне ⚙ (`aiSettings()`); `aiGetKey()`/`aiGetModel()` отдают ключ и модель выбранного ИИ, `aiName()` — его имя для подписей.

Одна страница настроек ИИ и ключи через Google Диск (18.11.2026, позже в тот же день). Ключи, модели и выбор ИИ меняются только на общей странице `https://luzinoff.github.io/budget/settings.html` (файл `settings.html` в репозитории бюджета, локально — `Budget\settings.html`); кнопки ⚙ / «Настройки ИИ» во всех трёх приложениях ведут туда (`luzOpenSettings()`, с `?from=` для кнопки «Назад»; с диска — `../Budget/settings.html`). На странице есть кнопка «Проверить» — пробный запрос к выбранному ИИ. Синхронизация между устройствами: `luzSettingsSync(tok)` (общий блок во всех трёх файлах) после каждого обмена с Диском читает/пишет `luz-settings.json` в appDataFolder (у трёх приложений один Client ID — папка общая). В файле поля aiKey, aiModel, aiProvider, dsKey, dsModel и `_ts`; Client ID не синхронизируется. Слияние целиком по `_ts`: `luzShared.push()` ставит `_ts` при правке любого поля, кроме clientId; страница настроек — при каждом сохранении. Если пришло с Диска — `luzBudgetOnShared()` / `luzDiaryOnShared()` / `luzMedOnShared()` (их же зовёт событие storage). Решение владельца: ключи теперь лежат и на его Google Диске (раньше — только в браузере). Service worker бюджета (`budget-v45`) кэширует `settings.html` под своим адресом, чтобы не затереть `index.html`.
